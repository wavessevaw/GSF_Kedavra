# Kedavra Hardware-Native Runtime: исследование

Дата: 24 октября 2026. **Research Only.** База — GSF Kedavra 1.4.1, commit `5f22938b55f9853f764e927c847d9c1a8d9a8c04`. Ветка: `research/kedavra-hardware-native-runtime`. В этом каталоге нет изменений рабочего движка, установки Gamescope, Mesa, kernel или релизов.

После первоначального аудита три направления реализованы в изолированном [экспериментальном PR #79](https://github.com/wavessevaw/GSF_Kedavra/pull/79). Документы 01–10 описывают исходную 1.4.1. [11 — новое сравнение с 1.4.1 вне Deck](11-NON-DECK-COMPARISON.md) содержит измеренный эффект C1, контрольные результаты и границы проверки DirectScan/completion.

## Вывод

Более экономичный тракт технически обоснован, но его преимущество на Steam Deck OLED **не измерено**. Самая предметная возможность — дать финальному warp писать в framebuffer, который Gamescope сможет передать своему DRM backend без ещё одного полноэкранного чтения и записи. Это условный fast path, а не отдельный compositor и не передача DRM master другому процессу.

Три первых инженерных задания:

1. **A1/A2: DirectScan с сохранением Gamescope как владельца вывода.** Выделять storage + sampled + flippable images, заранее проверять format/modifier/plane, выносить подготовку Kedavra перед выбором scanout/composite. Для несовместимых кадров использовать обычную композицию. Начать с SDR, затем отдельно доказать эквивалентность HDR, Mura и overlays.
2. **B1/B4: фактическая готовность пары + измерение задержек + ограниченные порции анализа.** Заменить фиксированное обещание `latch+2` на наблюдаемый timeline point с идентификатором пары и epoch. Отправлять анализ только при достаточном slack, не ставить заведомо опоздавшую зависимость перед финальным warp.
3. **C1: последний post pass пишет прямо в history slot.** Устранить отдельный `RecordCopy(post → ring)`, сохранив тот же порядок фильтров, формат, цвет и анализ. Это небольшой кандидат, пригодный и при недоступном DirectScan.

Это ранжирование по конкретности устраняемой работы и риску, а не по обещанным процентам ускорения. Governor — следующий потребитель корректных измерений; отдельная compute queue — более поздний эксперимент.

## Что установлено

| Факт | Класс | Следствие |
|---|---|---|
| `WantsComposite()` принуждает композицию во время генерации | CONFIRMED | Сейчас прямого вывода результата Kedavra нет |
| `CreateImage()` задаёт sampled/storage, без flippable/export | CONFIRMED | Текущий `pOutput[2]` нельзя просто передать в atomic commit |
| Gamescope умеет storage + flippable allocation через modifiers/dma-buf/backend FB | CONFIRMED | Не требуется заранее проектировать отдельный GBM allocator |
| Gamescope уже выбирает compute-only family и запрашивает realtime при CAP_SYS_NICE | CONFIRMED для кода | «Включить Async Compute» само по себе не нововведение |
| `OnPaint()` вызывает `on_me(...,vblank+2,true,false)` до выполнения анализа | CONFIRMED | Scheduler видит прогноз готовности, не завершение GPU |
| Возможность отдельных compute queues в RADV зависит от hardware-reported rings | SUPPORTED | Количество queues и разрешённые priorities нужно снять с конкретного Deck |
| Для VANGOGH используется DCN 3.0.1; upstream MES discovery не подключает MES для GFX10.3.1 | CONFIRMED для исследованных исходников | Не строить проект на MES и не менять firmware |
| Снижение GPU ms, watts и latency предложенными изменениями | HYPOTHESIS | Нужны A/B/A на Deck |

Доказательства и точные функции — в тематических документах и [реестре источников](10-SOURCES.md). CONFIRMED поведения исходника не означает проверенную производительность устройства.

## Границы доказательств

Работа выполнена на Windows без подключённого Steam Deck. Новые аппаратные испытания не проводились. Локально повторно разобраны исходные архивные CSV и gzip CSV; это **повторная обработка старых аппаратных наблюдений**, не измерение 1.4.1 и не проверка нового runtime.

В `bench.json` обнаружен RADV `Mesa 26.0.0-devel (git-d246f60ddf)`; префикс разрешён в `d246f60ddf53089faa1d554865f7a38a737ed388`. Исследован этот исходник, а также сравнительный tag Mesa 26.0.0. Номер kernel старого Deck и полный manifest установленного текущего SteamOS отсутствуют. Linux v6.16 — явно обозначенный reference snapshot, не выдаётся за kernel пользователя. Результаты применимости привязаны к capability gates в [08](08-EXPERIMENTS.md).

Архивный Auto run 10:53: актуальный анализатор учитывает 384 незарегистрированных слота и даёт missed_fraction 0,0077515 (0,775%), сохранённый отчёт — 0,0026857 (0,269%). Разница — методика, не ухудшение устройства; потерю logger нельзя исключить. Даже своевременный flip не доказывает новую картинку. Подробности и raw provenance — [08](08-EXPERIMENTS.md).

## Шкала доказательств

- **CONFIRMED** — исполняемый путь исходника, спецификация либо воспроизводимый результат с указанной областью действия.
- **SUPPORTED** — интерфейс/аппаратный механизм существует, интеграция или capability конкретного Deck не проверены.
- **HYPOTHESIS** — ожидаемая польза, требующая измерения.
- **BLOCKED** — конкретный отсутствующий capability или ограничение маршрута; указан способ проверки.
- **REJECTED** — нет основания ожидать полезный результат либо затраты/риск неприемлемы.

Аппаратные эффекты новых решений на Deck: **Не измерено**. Результаты software Vulkan-сравнения с 1.4.1, выполненного позднее, сохранены в [11](11-NON-DECK-COMPARISON.md); их область действия ограничена указанной CPU-средой. Сохранение качества, реального FPS и штатных ограничений мощности обязательно.
